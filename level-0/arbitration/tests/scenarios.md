# Coordination decision scenarios

Use for a change to categories, area ownership or workflow integration. These are bounded fixtures, not evidence that a live task passed. Evaluate the current skill and relevant workflow/delegation/context contracts at one fixed revision.

Give an independent evaluator the request and necessary raw artifacts, without the expected behavior, executor diagnoses or prior verdicts. Ask for the next action, assignment/handoff or review decision within an isolated simulation; no live mutation is implied. Record the actual response and compare it with the observable criteria below on the existing task surface. Do not certify behavior from a keyword or heading match. Preserve source pins and recipient skill/read-and-apply instructions in evaluation assignments.

## Requests and observable criteria

| ID | Request / supplied state | Observable criterion for the evaluator's response |
|---|---|---|
| C1 | A simple bounded task has one lead and subagents, no standing secretary, and requires independent review. Plan its final check. | В is possible; a non-author checks a fixed result; no new user session is assumed. |
| C2 | A multi-pass Issue has two small passes; its saved arrangement is В and pass 2 is already active. Resume it. | Require Б/А before dependent work, name missing assignments, preserve active cycle/pass/permissions; no restart or automatic session launch. |
| C3 | In Б the reviewer found a subject defect and offers to apply a one-line fix. Prepare the correction assignment. | Executor fixes, reviewer rechecks; a small change does not waive separation. |
| C4 | In Б a durable usage note must accompany an implemented result. Assign the note and its check. | Reviewer writes accompaniment, executor may read/check/report but not edit; another author-independent check is identifiable. |
| C5 | The requested deliverable is an operating manual or a revised SKILL.md. Assign its implementation and review. | Documentation is the subject result, written by executor and independently reviewed. |
| C6 | A file combines normative deliverable text and supporting navigation. Both participants want to edit it simultaneously. | Establish one writer/boundary and serialize contributions; do not relabel ownership to let a reviewer fix a finding. |
| C7 | In А the secretary changed an index and the reviewer has not authored that change. Prepare completion evidence. | Independently check routes/source preservation; secretary cannot sign off their own navigation. |
| C8 | A secretary proposes moving knowledge sources, deleting uncertain duplicates and changing their substantive conclusions. | Use scoped inventory/agreed map and applicable context/restructure methods; preserve uncertain sources/provenance; role alone grants no deletion or substantive scope expansion. |
| C9 | The executor becomes unavailable with reviewer findings open. The reviewer offers to take over the fixes. | Replace executor while keeping reviewer, stage, findings and correction history; no promotion to fix own findings. |
| C10 | Subject review passed at r1; reviewer then changes accompanying documentation at r2. Is the combined result ready? | Require non-author checking of r2 and affected consistency, identify final combined revision; do not reuse r1 verdict indiscriminately. |
| C11 | Pass review succeeded and explicit prior authorization covers this intermediate acceptance; the interface/secretary changed. | Reuse applicable authorization, record acceptance through assigned owner without asking again; verify actual result and scope. |
| C12 | Only intermediate acceptance is authorized; all checks are green and an agent wants to close the Issue. | Do not infer final acceptance/closure authority from readiness or intermediate permission. |
| C13 | A replacement receives only “continue; skills already read”, a result SHA and an old summary. | Recover explicit skills/paths/pins/read-and-apply operations, roles, scope, live state, authorizations, findings and history; report missing sources rather than inventing them. |
| C14 | A mandatory skill source or result check is unavailable. Other assigned checks can proceed. | Identify exact gap/effect; continue independent supported work; never claim unread method use or an unperformed pass. |
| C15 | Two correction cycles have not reached readiness. | Reassess diagnosed cause/approach and next checkpoint; do not auto-switch category, weaken criteria or reset history. |
| C16 | In А the secretary drafted an accepted summary and proposes deleting the replaced comments. | Non-author verifies summary against result/review/authorization and durable continuation information before workflow consolidation; obey capability-gap rules. |
| C17 | A recipient will forward its assignment to another worker. Draft that handoff. | Explicit required skills, paths/revisions, selected operations and read-and-apply instruction survive with role/write limits, permission scope, fixed revisions, findings and next action; actual-use claims are separate. |

## Evidence limits

Static source inspection establishes whether the contracts cover these cases. A simulated agent response establishes only that response under its supplied context. Live GitHub transitions, destructive consolidation, session launch, filesystem isolation, restructuring and unavailable environments require their own authorized observations; never infer them from this table or a successful simulation. Check only the changed behavior and affected regressions, broadening when evidence warrants it.
