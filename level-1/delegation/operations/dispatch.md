# Dispatch, continue and follow work

Use for the current assignment, including a worker's own execution. Apply the [shared contract](../SKILL.md) and established plan; spawning is optional, not the operation's default side effect.

## Prepare an accessible task package

Include the information the recipient needs, proportional to the work:

| Part | Required content |
| --- | --- |
| Outcome | Goal, scope, current task/unit and completion criteria |
| Inputs | Authoritative sources, exact relevant revision, artifact locations and usable access route |
| Decisions | Settled requirements, preserved behavior, open questions and current dependencies |
| Authority | Assigned role, write scope, constraints, existing permissions and explicit spawning rights/limits |
| Method | Enumerated required skills, source paths/pins, selected operations/resources, and direct instruction to read and apply them |
| Return | Expected artifact/result, verification evidence, report format and next checkpoint where needed |

Include every project-required contract and the skills applicable to the assigned work and role. One exact shared source pin may cover several enumerated skills. Do not replace this list with “follow applicable skills,” a parent's acknowledgement, or a reference to inaccessible prior conversation. Critical constraints belong in the package itself.

Preserve the list, read-and-apply instruction, pins, decisions and role/permission boundaries through forwarding, replacement and descendant dispatch. Supplement newly applicable skills at the established source revision and within authority; read their supporting resources progressively. Do not silently promote a different shared version during continuation. A fresh source may be investigated without becoming the active contract by accident.

Workers use this package as their entry point and retrieve missing sources under applicable project rules. Parents need not pre-read every source a worker will investigate. If a required source is inaccessible, report the specific gap and effect; continue supported independent work without claiming the unread method was applied.

## Bind the package to the actual interface

Use the matching runtime profile only for actions it actually covers. Select the permitted task type, model/route where supported, context mode, tools and writable area. A requested setting is not proof it took effect: inspect the returned task identity/status and relevant effective settings when exposed.

Prefer task-specific context. Inherit conversation only when materially useful and compatible with the assignment and interface. History inheritance still requires an explicit task package and may expose irrelevant diagnoses to a supposedly independent checker. Context isolation does not isolate files or automatically preserve permissions.

Do not change runtime configuration, install a strategy or select a new paid provider merely because the plan prefers another model. If the interface is synchronous, account for blocking before scheduling dependencies. If it is asynchronous, record the returned identifier and expected completion route. Do not report a failed or refused launch as a running agent.

## Follow progress and continue

Do useful non-overlapping work while children run. Prefer completion notifications or appropriately spaced waits over repeated polling. Set a checkpoint only when latency, risk or a known deadline makes it useful; there is no universal task duration.

Track meaningful progress: new evidence, completed artifacts/checks, remaining questions and repeated non-progress. A busy process, optimistic status or repeated tool calls alone do not show useful progress. On an expected-duration breach or clear stall, request an interim result when supported, then use [recover](recover.md); do not wait indefinitely.

Reuse a participant when its context and permissions still match. Send changed requirements and affected source revisions explicitly. Recheck any previously accepted contribution invalidated by new inputs or results. Reuse is not an independent fresh review, and changing a model hint may not alter an already running/resumed participant.

When the interface cannot steer, resume, observe or cancel as desired, use its documented available route and disclose the material limitation. Do not simulate a cancellation by merely ignoring a child that may still write.

## Return work

Use the root's compact result contract. Include concrete artifacts/source revisions, actual checks, unresolved requirements and needed decisions. Keep requested settings distinct from effective settings when only one is known. A timeout or interruption can leave usable partial evidence; label its scope instead of silently dropping it or calling the task done.

Report which required skills were actually read and the relevant evidence of use. Keep evidence and limitations with the result, even if earlier progress updates mentioned them. Parents inspect and combine contributions through [integrate](integrate.md); a child completion signal alone is not task acceptance.
