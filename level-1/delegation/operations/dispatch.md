# Dispatch an in-context child

Use the [shared contract](../SKILL.md) to establish that a child is warranted. Work from the current task surface. Each unit needs identifiable inputs, a coherent result, dependencies, an owner and a check. Launch only ready independent units concurrently. If an unknown blocks decomposition, resolve it directly or give a child a bounded investigation before assigning dependent work.

## Prepare an accessible task package

Include the information the child needs for the assigned result.

| Part | Content |
| --- | --- |
| Assignment | Goal, current scope, parent, contribution owner, intended result and completion criteria |
| Inputs | Authoritative sources, exact relevant revisions, artifact locations and a route the recipient can use |
| Decisions | Settled requirements, behavior to preserve, pending dependencies and bounded open questions |
| Permission | Role, permitted tools/effects and write area, explicit descendant grant or prohibition, and applicable tree/resource limits |
| Method | When the task requires skills, enumerate their source paths, exact pins and applicable operations/resources. Instruct the child to read and apply them. |
| Return | Expected artifact and version, checks and evidence to return, delivery destination and any necessary checkpoint |

Give critical constraints directly. A shared pin can identify several enumerated resources. A mention of the instructions or their presence in inherited history does not establish that the child read or applied them. For a non-author check, supply the raw material, fixed review target and criteria. Keep author predictions and grader answers out of the package.

The child uses this package as its entry point and resolves missing accessible inputs under the assigned rules. The parent need only verify the source route and the evidence required to prepare and check the assignment. If an input is inaccessible, return the precise gap and continue supported work. Carry the package, pins and prior permissions through continuation, replacement and allowed descendants. State material changes and preserve earlier decisions and usable evidence.

## Bind the package to live controls

Check the relevant environment facts before launch.

- **Action and route.** Verify that the tool and permission are present. Use [model selection](../references/model-selection.md) to check permitted and selectable routes, actual fixed or inherited settings, and fallback. Record what is requested and the effective settings that can be verified.
- **Context and access.** Expose only needed context. Use inherited history when useful and compatible with the route and checking requirement. Verify needed tools, modality, source access and the writable area from the child's perspective. Context isolation does not establish file isolation.
- **Ownership and capacity.** Keep one active writer per area. Check the tree, depth, live and queued work, available capacity and tighter limits. Grant descendants only when explicitly assigned and supported. A child without a grant returns the need to its parent. Verify any authorized filesystem isolation before relying on it.
- **Delivery and effects.** Check how the tool identifies a launch, delivers results and permits continuation or cancellation. Account for synchronous blocking before scheduling. Check current restrictions on configuration, providers and spending before considering any route.

Use the matching reference only for controls it describes and confirm against the live schema. Keep assignment updates concise. Identify the chosen route and rationale when relevant, and announce material tree or limit changes. A rejected launch starts no work. If the outcome of the launch is ambiguous, establish its state before issuing an overlapping request.

On launch record the returned identity, input revision, write scope, route evidence and completion channel. While work is running, use [collect](collect.md).

## Return a contribution

Return the applicable details on the agreed task surface.

`status (done, partial, blocked, error or cancelled) | result | artifact and revision | sources/pins | evidence and checks | remaining work, cause and next action`

Include which assigned methods were actually read and applied and the evidence of their effect on the work. Name inaccessible inputs, omitted checks, any unresolved background work and the scope of useful partial results. Distinguish reported settings from effective settings when that matters. Return concrete findings and evidence pointers.
