# Place the improvement at its owner

Use `context` to resolve the subject owner, authoritative evidence and authorized update destination. This reference selects the resource for a learning candidate; it does not replace those ownership decisions or grant access. Check the actual source revision and existing content before creating another home.

| What the evidence changes | Candidate destination | Preserve |
| --- | --- | --- |
| Task execution departed from adequate instructions | Current task output/execution; no method edit for that error alone | The adequate reusable method and its legitimate variations |
| A project constraint, binding, accepted choice, path or runtime setting | Existing project-owned requirement/configuration/reference or a proposal to that owner | Local activation/permission constraints; do not copy live values into the shared skill |
| Knowledge exists but the applicable reading path cannot reach it | Owning index, link or task route; method only if separately deficient | One canonical method; enough route context to select it correctly |
| An operation omits a necessary action, condition or recovery branch | The owning operation or its subject reference, where the action is used | Existing successful branches and their conditions; no unrelated root rule |
| Explanation, diagnostic model or boundary knowledge is insufficient | The existing subject reference, linked from its applicable operation | Progressive loading; root remains a compact selection/contract surface |
| Agents need a concrete demonstration of an already justified mechanism | A worked example with inputs, steps, checks and limits at the subject owner | General method authority; illustrative facts are not live project requirements |
| Repeated deterministic work needs a reusable implementation | An owner-local tool with explicit contracts and exercised checks | Permissions, runtime profile and existing implementations; do not install new infrastructure implicitly |
| A protected behavior or missing boundary needs durable coverage | Owner-local fixture/test with meaningful inputs and observations | Distinguish tests of implementation, agent behavior and target-runtime behavior |
| The skill's shared selection/authority contract itself is wrong | The root contract, only when evidence specifically supports that scope | Concision, compatible compositions and existing ownership/permission boundaries |

Choose the smallest coherent set, not necessarily one file. A corrected operation can require its route, example and protected test to change together. Conversely, finding the same fact in several summaries is not a reason to maintain several canonical copies.

## Shared source and local adaptations

Separate the transferable method from a target project's adaptation. An improvement to a shared source does not automatically update adopted pins, installed copies, local maps, graphs or downstream projects. Keep the revision actually used and the proposed adoption action visible. Preserve supported local adaptations; if a candidate conflicts with one, establish its authority/applicability at the owner before changing it.

Keep transient hypotheses, unsuccessful attempts and raw run history on the current task surface. Integrate accepted reusable knowledge at its canonical method owner through the governing task process; retain only the provenance and limits that future use needs. Existing Issue summaries remain task records, not another learning ledger.

If a destination or material authority rule remains unresolved, identify the gap and return a scoped proposal/deferred decision. Directory proximity, technical writability, newer timestamps and repository identity do not establish knowledge ownership or permission.
