# Prepare and refine the owned candidate

Use this operation after a reusable hypothesis is supported, or when the task already supplies equivalent evidence. Do not repeat observation/generalization merely to fill a sequence. Keep [evidence and scope](../references/evidence-and-scope.md) and the current task's permissions in force.

## Locate the smallest coherent change

Use [placement](../references/placement.md) to identify the canonical owner and resource. Read the relevant current method, its callers/links and affected examples/tests at an identified revision. Compare with the revision actually used in the episode; a later fix can remove the need for another edit. If the task pins an older adopted version, preserve that distinction rather than silently switching its active revision.

Choose the mechanism that resolves the demonstrated gap: repair a route, add a conditional step/diagnostic branch, deepen a reference, supply a worked example, or correct a reusable tool/test. Avoid a new general rule or root expansion when an existing subject owner can carry it. Include the dependencies necessary for the branch to work, without unrelated cleanup.

## Make the plan reviewable before editing

Use the existing task format or adapt the optional [improvement form](../templates/improvement.template.md). State:

- Hypothesis and expected observable improvement, with source evidence and the method revision actually used.
- Applicability, exclusions and unresolved alternatives; distinguish observed success from suspected causation.
- Owner/destination and intended change; protected behavior, valid local adaptations and concurrent work to preserve.
- Current write/publication authority and any missing access/runtime. Write authority and authority to publish, accept or modify downstream users are separate.
- Planned original, transfer/boundary and affected-regression checks, with inputs, expected observations and the evidence each could establish. Name target-runtime checks separately from static/mechanical/model checks and retain unavailable checks as gaps.

Reuse a check when it covers several concerns. If no regression behavior is affected, explain that relation rather than inventing an unrelated suite.

If the owner is outside current write authority, return this proposal and stop before editing. Do not write a shadow copy, change another repository, install a helper or publish elsewhere to bypass the boundary. If a proposed change alters a user-owned decision or an accepted invariant outside scope, return that decision through the existing task process; continue separable authorized work.

## Make a bounded candidate when authorized

Recheck the destination before writing; preserve unrelated updates since the baseline. Make the planned change at the owner, keeping conditions, failure diagnostics and evidence limits next to the relevant step. A reusable tool needs a defined input/output/error contract; a static test or example cannot certify an unexercised native implementation.

Inspect the diff for root growth, duplicated instructions, leaked project/private data, lost adaptations and unintended changes. Include narrowly necessary route/test updates. Keep the pre-edit plan and actual changes distinguishable; if new evidence changes scope or checks, record the reason on the existing task surface before dependent work.

Return the candidate's exact revision/artifact, changed owner, actual checks and remaining planned checks. A proposal is not an edited candidate, an edited candidate is not verified by its prose, and passing checks are not task acceptance. Use the governing task process for subsequent verification/correction/rollback/acceptance; this operation supplies no new lifecycle or approval ceremony.
