# Generalize within the evidence

Use this operation to decide whether a meaningful episode supports a reusable candidate. Reuse an existing evidence slice; use [observe](observe.md) only when the decision lacks it. Apply the cause and evidence distinctions in [evidence and scope](../references/evidence-and-scope.md).

## Diagnose the mechanism

Compare the prescribed method, actual execution and expected/observed outcome under the same relevant conditions. Ask what would have to change to explain the difference: instruction, reading route, input/profile/permission, execution, or a project-owned choice. Mixed causes need separate destinations; do not rewrite an adequate API method because its environment profile was unreachable.

State a conditional hypothesis: **for this input/operation/profile, changing this step should improve this behavior because of this mechanism**. Identify a competing explanation when it would change the proposed remedy. Select a check whose outcomes would distinguish those explanations, with required input/runtime/access and a stopping condition. If no authorized check can settle a material uncertainty, retain it and defer the affected claim.

For a useful success, identify the repeatable technique and the result actually checked. Success may justify trying a bounded branch even while the initial failure's cause is unknown. Do not convert that observation into a causal guarantee: distinguish "worked under these recorded conditions" from "this mechanism always prevents failure."

## Bound transfer

- Name the conditions that matter to the mechanism, and what may vary without changing it. Separate a reusable procedure from local identifiers, values, paths, policy choices and permissions.
- Name at least one boundary where the change is unnecessary, unsupported or harmful. A procedure for independent records does not establish correct handling of records with cross-dependencies.
- Treat one supported counterexample as enough to propose a narrow missing branch. Repetition across projects can help investigate transfer, but neither a count nor agreement/silence proves universality.
- Check the actual owner for an existing adequate technique. If it already exists, use it; a broken discovery route may justify a navigation candidate rather than another copy of the method.

Use evidence sufficient for the current decision. A counterexample can justify a candidate without verifying its replacement; a successful fixture does not verify another runtime. Keep a broad idea deferred while progressing on a narrower supported hypothesis when those claims can be separated.

## Return a disposition

Return one compact result with evidence and limits:

| Finding | Result |
| --- | --- |
| No distinct reusable gap remains | No skill change; correct task execution or resolve the local/context issue through its owner if needed. |
| A project choice/configuration is the useful knowledge | Authorized project-local update or proposal; no shared rule based on that value. |
| A supported conditional method or route improvement is identifiable | Bounded candidate hypothesis; select its owner/resource through [placement](../references/placement.md), then use [refine](refine.md) for the change plan. |
| Material evidence or authority is missing | Name the gap and next discriminating check; defer the claim, or return a supported proposal when only write authority is absent. |

This disposition neither accepts the candidate nor starts a different task, Issue, agent allocation or installation.
