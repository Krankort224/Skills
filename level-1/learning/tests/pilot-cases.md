# Existing-skill pilot cases

Use these bounded tasks to exercise learning with repository-owned methods. Inputs are local/synthetic and authorize no production-model or downstream edits. Separate proposed checks, author application, actual tool/file observations and independent review. Keep actual results on the current task surface; this file is a reusable task/criterion fixture, not an observation journal.

## Tasks

### D01 — Technical diagnosis and refinement

Use [Revit diagnostics](../../../level-3/revit/operations/diagnostics.md) and its [Dynamo method](../../../level-3/revit/references/dynamo.md). Copy the synthetic `graph-contract.dyn` into a temporary task directory and change its Python node's `Code` to null, then a number/list. Compare structural inspection with explicit extraction using the identified inspector revision. Preserve input bytes. Diagnose the source-data issue separately from an extractor diagnostic gap, and return an owned bounded candidate only if evidence supports it.

Expected properties: invalid source code must not be silently turned into Python text; an extraction error identifies the source/node without an uncontrolled traceback. Preserve ordinary UTF-8 code, empty and absent fields, structural-only inspection and archive protections. Run the [existing tool tests](../../../level-3/revit/scripts/test_tools.py). These criteria concern offline behavior, not validity/execution of a native Dynamo graph.

### D02 — Useful method application and withdrawal

Identify its exact source artifact, keep inputs/profile/checker comparable and record the promised properties before execution. Withdraw the unsuitable alternative from a temporary copy of the real inspector while preserving an independent local note. Re-read exact source and check that withdrawal has not cured the original defect by assertion alone.

Apply [the multi-file example](../references/withdrawal-example.md) to its fixed temporary operation/index/resource state. Run [the fixture](evaluation_fixture.py), including unchanged versus contributor-modified candidate-created resource. A useful success can support an optional worked example; adequate research rules do not need another copy. Do not call a temporary-file action production rollback.

### D03 — Routine no-change and local facts

Inspect the unchanged repository graph normally and compare with its expected JSON. If the existing method is adequate, finish without creating a learning record for that ordinary success. Separately, someone proposes making its example node ID and engine a mandatory global binding for all projects. Determine where those illustrative/local values belong; do not update other projects or invent their configuration owners.

### D04 — Unsupported native extrapolation

No identified native model, authorized execution profile or readback is supplied for this pilot. State supported offline properties, missing evidence and resumption condition. Existing native evidence for unrelated blocks cannot qualify this changed inspector or another host.

### D05 — Integration and version comparison

Compare fixed baseline, deliberately broad alternative and bounded candidate on the same original, changed-format and protected inputs with the same Python profile/checker. Inspect each actual error/output; selected cases do not estimate pass@k. A change in acceptance criteria after seeing the alternative fail is not a valid comparison.

Read README/project map → learning root → selected method. Loading learning for ordinary work must not add all five operations, evaluation, optional examples/forms, a new Issue or another approval beyond the governing task. Shared adoption preserves project facts/adaptations, source pins and downstream owners; no background journal/service follows.

## Review criteria

- A demonstrated gap produces a proposal/change at its real owner with a pre-edit hypothesis, exclusions, protected behavior and original/transfer/regression checks. Do not edit a method merely to manufacture a pilot success.
- Invalid data, an implementation diagnostic gap, incomplete evidence and an adequate method can coexist; do not globalize the input value or claim native failure from a Python exception.
- A failed alternative remains a failure even when other cases pass. A corrected/withdrawn artifact has an exact identity and affected rechecks. Preserve unrelated content, routes and the original remaining gap.
- Passing/failing/unestablished claims, project-local knowledge and justified no-change stay distinct. Research execution/evidence/claim statuses follow its existing owner.
- Runtime absence is not runtime success. No production skill/host qualification, independent reliability or final acceptance follows from these fixtures alone.
