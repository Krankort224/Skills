# Maintain project references

Use when the task explicitly requests initialization, refresh, reconciliation or fixes to project context references. The supported slice maintains the meaningful project map and, when explicitly requested, prepares a bounded structural graph in fresh staging. Explicit semantic construction adds current-agent source reading and native mixed staging. The tested Linux Python/Markdown lane also supports conservative semantic-shard reuse and coherent Git-commit trio publication when authorized.

## 1. Establish the authorized change

Identify the target project/root and applicable branch/worktree/scopes. Locate its project-owned context references and any existing map, checking declared identity and path conventions. A shared skill's source-project map is not the destination map; resolve the destination independently before editing. Read enough task-relevant sources to resolve facts, owners, authority and uncertainty using the shared read method; do not repeat already verified unchanged material.

Determine which references the task authorizes changing. A request to update the context map authorizes routine edits to that map, not edits to every canonical owner it cites. If the broader task separately authorizes a canonical correction, make that change at its established owner through the applicable task/skill; then reconcile the map with the result. Do not create an Issue, branch, new document taxonomy or downstream installation merely to maintain the map.

Resolve material destination or authority gaps before the dependent edit. Continue independent supported changes; preserve unresolved facts as explicit gaps rather than filling them with a guess. Existing authorization does not require another approval for ordinary scoped reference maintenance.

## 2. Initialize a meaningful map

If the target project's map does not exist:

1. Identify the project's purpose and material scope from its authoritative instructions/current sources. Inspect the main entry points and enough of each relevant component to establish roles and actual interactions.
2. Sketch its system/component hierarchy. Explain what each major part does, what it consumes/produces, and how the parts cooperate. Include meaningful boundaries (for example, experiment versus supported product) only when sources establish them.
3. Identify current knowledge owners, authority rules by subject, material constraints, immutable inputs and authorized destinations. Support important overview claims with source paths/sections or other verifiable locators.
4. Add stable routes for the project's real recurring questions, including when direct implementation/data/tests are necessary and when history is relevant. Retain only categories that help this project.
5. Use the shared `repository.template.md` as an adaptation starting point when available, filling it from the target project's verified sources rather than copying the Skills map. During adoption, transfer reusable skill resources without the source project's completed map or generated graph trio; create only the destination-owned references authorized by the task. If the template is absent from an installed skill, the criteria above are sufficient: do not block, fetch/install a template or copy placeholders into project knowledge. Source templates stay in Skills; the adopted project gets the completed `repository.md` without the `.template.` marker.

A useful opening tells a new agent what the project is and how it works. A tree/list of files, a table of source links or copied canonical prose alone is insufficient. Keep the overview compact enough to route reading while explaining the relationships that would otherwise have to be rediscovered.

## 3. Refresh without erasing local knowledge

Updating reusable skill resources does not authorize replacing the destination's map or graph with source-project artifacts. Preserve those files and assess any requested refresh against destination sources and the current profile.

For an existing map, compare task-relevant claims and routes with current owners and actual paths. Preserve project-specific sections, language, valid annotations and local adaptations. Patch obsolete material at the smallest coherent scope; do not regenerate the whole map from a generic template.

Account for:

- **changed facts or decisions:** verify their subject owner and scope; update only the map's useful overview/navigation, leaving detailed contracts at the owner;
- **renamed/moved sources:** verify continuity before changing references; preserve distinctions between similarly named scopes/components;
- **deleted sources:** establish whether the owned knowledge moved, was retired or is genuinely missing; record a material ownership gap if unresolved;
- **new components/interactions:** add enough role/relationship explanation and a route to the authoritative detail, not one row per file;
- **branch/platform/experiment differences:** qualify the claim where it applies; do not promote a prototype or another branch's behavior into current scope;
- **conflicts/history:** remove a superseded claim from current overview while retaining a justified history route; preserve genuine unresolved alternatives and their evidence;
- **derived material:** record useful graph/report availability and known coverage limits without treating artifacts as owners or rewriting them in this map-only operation.

Separate intended design, actual behavior and source uncertainty when they differ. A canonical defect found during reference work is a finding/destination for the owning task; do not silently change implementation to make the map true. Do not restate whole policies, source documents or historical conversations in the map.

## 4. Validate the proposed map and write it

Before replacing current content, check the complete proposed result against its owners:

- purpose, component roles/interactions and task-relevant constraints are correct and sourced;
- routes and source locators resolve under a stated path convention;
- scopes, ownership/authority and intended-versus-actual distinctions agree with project instructions;
- no template placeholders or mandatory empty categories remain; uncertainty is explicit;
- local adaptations/language and immutable-source boundaries are preserved;
- history, Issues and derived outputs have their established roles;
- no secrets, host-local absolute paths, unrelated changes or invented completeness claims were introduced.

Prepare the complete intended edit before writing, preserve the last good map if a write/validation fails, and use the project's normal editor/file-change method. Inspect the resulting diff and re-read the saved map; verify material changed claims/links and answer representative project questions from the result. A file successfully written is not proof of accurate context.

Use ordinary existing publication/versioning instructions when publication is part of the task. The context operation does not add its own branch/PR/acceptance lifecycle or authorize unrelated writes.

## 5. Keep graph evidence honest

The shared `references/graphify/.gitkeep` is an empty location reservation, not a generated graph or a maintenance result. Never replace it with dummy JSON/HTML/report data. Reviewed real graph artifacts belong together in this directory after authorized construction and coherent publication; tools/procedures remain outside it.

For map-only work, keep existing graph artifacts untouched. Disclose known stale graph claims where useful; a map refresh does not update the graph, and a missing graph does not prevent a useful map.

Select only the authorized graph method:

- [Build](graphify/build.md) prepares initial structural or active-agent mixed evidence in fresh staging, with complete selected-source reading and source-backed interpretation.
- [Maintain](graphify/maintain.md) assesses a prior immutable trio, chooses no-op/reuse/re-extraction, reconciles current evidence and handles authorized coherent publication/recovery.
- [Export](graphify/export.md) inspects presentation or creates selected separate interchange/cross-repository views with explicit output ownership.

Each method links its technical recipes and supported boundaries. Preserve last-good references on failure, keep unknown/unsupported coverage explicit and use the project's existing authorization and workflow for publication. Staged artifacts and optional views are distinct from a published current trio.

Report what reference material changed, why, which source evidence and representative checks support it, and what remains unresolved or out of scope. Distinguish a completed map update from graph construction/semantic extraction/tool preparation that did not run.
