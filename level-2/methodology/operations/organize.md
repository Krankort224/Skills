# Organize existing material

Start at the requested section. An inventory supplies observations, a design supplies a map, a migration changes the material, and a review reports findings. Use the user's scope, current evidence and existing authority across handoffs.

## Inventory existing material

Inspect the actual filesystem or permitted metadata surface. Establish the affected project, physical root, revision or observed state. Start with names, paths and metadata. Check relevant tracked, ignored, untracked, generated, binary and LFS material, external references, cloud placeholders and local differences. Read selected local contents or history to resolve a question about role, identity or ownership. Use hashes when byte identity matters.

Separate observed facts from suspected relationships. Record which items are canonical, historical, derived or temporary, what establishes those roles, and which candidates remain ambiguous. For example, two copies named “final” need a release record or another source of authority to identify the issued copy. Deliver the scoped inventory with evidence pointers and unresolved items.

For cloud files, use exposed listings and metadata. Downloading, copying, exporting, synchronizing or otherwise materializing contents locally requires separate explicit, unambiguous authorization. Record the exact evidence missing when metadata cannot settle classification. Inventory alone authorizes no reorganization.

## Design the structure

Start from the defect someone encounters and what a successful structure must make possible. Establish the owner of the current version, how revisions become historical, which material is immutable, what is generated and what must be delivered. Create a group when its membership, access, storage or lifecycle differs in practice. Give each new name or level a purpose. Preserve names and external IDs used by tools or recipients.

Map each significant item or group from its existing location to its target and action: move, rename, merge, archive, leave, reference only, exclude from the repository, defer or mark unresolved. Describe merge handling, reference repairs, applicable Git/LFS rules and the checks that establish preservation. A repository exclusion leaves the local source in place unless disposal was separately agreed. Identify any proposed content edits separately from relocation.

Return the target, the map and choices that need a decision. An inventory or design request ends with that deliverable.

## Execute an agreed migration

When the target, map and authority are established, start here. Compare the affected state with the baseline, including immutable inputs, untracked material, unrelated edits and any pre-existing destinations. Reuse prior checks while they still describe the material. After a partial run, recognize completed moves from origin, destination and content evidence before applying outstanding entries.

Apply the agreed actions and required reference repairs. Keep enough origin evidence to trace important moves and preserve external identifiers. If an item is missing, the destination conflicts, or a new version appeared, isolate the affected map entry and explain the missing decision. Continue independent entries. An uncertain duplicate or unclassified item stays in its specified state.

Compare the actual result with the map. Account for moved contents, absences and unexpected copies, resolve internal references, and verify unaffected work, provenance, storage behavior and deferred positions. Report the before/after evidence, deviations and any inaccessible checks. Without write access provide the scoped instructions to the executor and identify the evidence still needed.

## Review an existing result

Use the baseline, agreed target and actual post-migration state. First check the material and moves, working links, preserved identifiers, unrelated changes and documented exceptions. Then repeat the task that motivated the reorganization. Can a recipient find the issued file and distinguish it from superseded copies? Can an editor identify the owner of the next change? A file count alone cannot answer either question.

For each material finding, identify the affected item, the expected and observed behavior, evidence and consequence. Separate a missed move or broken reference from a defect in the agreed design. Retain unresolved ownership or uncertain provenance explicitly and name the evidence that would resolve it. A review returns findings. Apply corrections or change the map when the task authorizes that work.
